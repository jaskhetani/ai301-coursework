# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-diff-alignment | The accepted plan's issue outcome, in-scope and out-of-scope boundaries, named files, approach, test changes, and `## Deviations`, read against every changed file and meaningful hunk in the candidate diff and the commit list | Every material production and test change implements the planned mechanism and falls inside the plan or a specific recorded deviation. Every material planned deliverable appears in the diff, unless the plan or deviation explicitly defers it and states the resulting boundary. Hidden extra behavior, unrelated cleanup, or silently omitted promised work fails; an honestly bounded and disclosed partial outcome may pass. | required |
| description-accurate | The candidate title and description, including issue, change, testing, limitation, and fidelity claims, read against the accepted plan and deviations, commit list, complete diff, and test evidence | The title and description unambiguously correspond to the issue, and every material claim about what the diff changes, omits, or demonstrates is accurate. No claimed file, behavior, test, documentation update, plan fidelity, or absence of side effects is contradicted by the artifacts. A material limitation passes only when the plan or deviation authorizes it and the description states it plainly. | required |
| test-evidence-decisive | The plan context's reproduction and test plan, issue trigger and controls, candidate test-evidence section, new or changed tests in the diff, and repository checks required by repo facts | The evidence reruns the issue-defining trigger through the changed path and shows an observable before/after result that distinguishes broken from fixed. It exercises every material failure mode the plan commits to verify, preserves a relevant control when the plan names one, and reports the applicable repository checks with concrete outcomes. Generic assurances, suite names without results, or evidence from an unchanged path fail. A reported check failure may pass only when its output is shown, the description discloses it, and the evidence establishes that it is unrelated to the changed behavior; failure on the changed path fails. | required |
| diff-reviewable | The complete unified diff and commit list, with each hunk classified as planned implementation, planned test/documentation, necessary mechanical support, or debris | The intended change and regression coverage are directly reviewable, and no debug output, commented-out experiment, dead helper, stale TODO, unrelated refactor, drive-by edit, duplicated code, or formatting/import churn materially obscures or enlarges the change. Commit wording alone does not fail an otherwise clean diff, but commits and hunks together must let a reviewer isolate the intended work. | required |
| repository-standards | The repo-facts block or, live, the PR template, contribution guide, policy files, and explicit issue-thread directions, read against the candidate title, description, checklist claims, disclosures, diff, and test evidence | Every stated mandatory submission requirement is satisfied with truthful content: required template sections and issue linkage are present; required checklists reflect the evidence; required tests, changelog or release-note files appear when the repository demands them; explicit maintainer directions are engaged; and every required AI-use disclosure names the tool and extent. Do not invent requirements when the repository states none. | required |

## Verdict rule

Grade every row `pass`, `fail`, or `unclear`. Accept only when every required check passes. Reject when any required check fails or is unclear. `Unclear` means the package lacks enough verifiable evidence to apply the pass condition and counts as failure; never fill the gap with assumptions. Preferred checks, if added later, may appear in the summary but never change the binary verdict.
